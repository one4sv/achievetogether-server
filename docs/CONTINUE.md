Проблема: API выдавал подписанные Storage URLs на 3600 секунд; после изменения приватности поста уже выданная ссылка оставалась действительной без проверки прав. У `posts` и `comments` бакеты приватные (`public=false`), но это не отзыва́ло действующие signed tokens.

Без миграции БД: `signedMedia`/`signedRows` теперь вместо Supabase signed URL выдают относительные `/api/post-asset/:postId/:index` и `/api/comment-asset/:commentId/:index`, в том числе `share` при законном просмотре по ссылке. `routes/system/post-assets.js` на каждом GET заново проверяет `readablePost` (`visiblePosts`, правила видимости, исключения, блокировки, share), затем проверяет URL Storage, путь и принадлежность посту и только после этого скачивает объект сервером. Для комментариев проверяется видимость родительского поста. Ответы имеют `Cache-Control: private, no-store`, `nosniff`, для видео работает Range; прямые Supabase токены больше не создаются API для постов/комментариев. Для немедленного отзыва необходима отдельная проверенная миграция путей объектов (или ротация подписывающего секрета с последствиями для всего Storage); автоматически не выполнять. ## 14.11.2026 — повторная отправка кода регистрации

Добавлен `POST /register/resend` для **pending_users** с email в теле запроса. Сервер проверяет существование неподтверждённого аккаунта, возвращает HTTP 429 и `retryAfterSeconds` до истечения **60 секунд** после исходной регистрации или предыдущей успешной повторной отправки. Условный `UPDATE ... WHERE created_at <= (now - 60 seconds)` в PostgREST не допускает конкурентного обхода таймера. При успешной отправке новый случайный код заменяет прежний и действует 24 часа; при ошибке email-провайдера старые данные восстанавливаются (если ещё актуальны). Пароли и коды в ответ API не выводятся. Браузер показывает состояние ожидания и обратный отсчёт. 2FA-вход не трогать: повторная отправка туда требует отдельной аутентификации (нельзя генерировать 2FA по одному email). Без изменений базы и миграций. Тесты: `tests/registration-resend.test.js` (cooldown, successful resend, delivery failure, unknown pending account), клиент `BodyMail`, документы клиента `AUTH_AND_SESSIONS.md`.

## 07.11.2026 — блокировка личного контакта и ATBot

- `GET /chat/:nick` **должен возвращать историю личной беседы**, даже если текущий участник выставил `chat_members.is_blocked=true`. Отказ 403 в этом месте мешал открыть ATBot для разблокировки; исправлено. Для `GET /chat/group/:id` блокировка членства по-прежнему означает бан, чтение запрещено.
- `POST /chat` запрещает отправку в личный чат, если любой из двух участников заблокировал другого, при этом история доступна. ATBot вызывается **только после** проверок прав и сохранения отправленного сообщения, а не до них.
- `POST /toggleblocked` больше не использует небезопасную для личных блокировок `get_shared_chat` (RPC мог выбрать двухпользовательскую группу). Чат подбирается только среди `chats.is_group=false`; из Acc, публикации или активности можно заблокировать пользователя без существующего DM — создаётся пустой приватный диалог. При блокировке не изменяются участники групповых чатов. Требуется валидный UUID, запрет блокировки себя.
- Автоматические проверки `tests/block-flow.test.js`: запрет блокировки самого себя и неизвестного пользователя, отсутствие побочных банов в группах, чтение заблокированной личной истории и запрет отправки до разблокировки. `POST /plans/:id/invite` теперь позволяет владельцу приглашать незаблокированный личный контакт в изначально личный план; при первой успешной записи pending-приглашения `one_off_plans.kind` меняется на `shared`, без пересоздания плана. Ошибка промоции отменяет только что созданное приглашение. `GET /plans/:id` возвращает принятых участников, а владельцу дополнительно pending-приглашения; owner отмечен `is_owner`, статусы `accepted`/`pending`. Счётчики выполнений используют только принятых участников. Новый `DELETE /plans/:id/members/:memberId` доступен лишь владельцу незакрытого плана и запрещает удаление самого владельца; удаляет участника/приглашение, связанные completion и личный комментарий. Проверить на двух авторизованных аккаунтах: переход personal → shared, списки pending/accepted, отмену инвайта, удаление, права постороннего и поведение после отмены плана. Дальнейшие вход по ссылке/чатам остаются в backlog.
